# VisiCore（视枢）架构评审与下一步优化建议

> 评审日期：2026-10-14
> 评审对象：工作区当前源码（`VisiCore.slnx`，API/Worker 2.2.0，桌面 2.2.0）
> 评审方式：全量源码通读 + 独立构建与测试复现 + 同类开源项目架构横向对比
> 结论口径：本报告只描述**当前工作区实测状态**，不代表线上发布包状态。

---

## 一、结论摘要

VisiCore 是一个**工程完成度明显高于其代码组织水平**的项目。业务闭环、可靠性设计、
接口契约纪律和验证证据链都相当扎实；主要债务集中在**抽象层缺失**——不是"代码写得差"，
而是"缺少几个关键接缝"，导致同样的逻辑在多处重复、在多处膨胀。

评审中最重要的三个判断：

1. **不要做 DDD/Clean Architecture 重写。** `Domain`（61 行）和 `Application`（19 行）
   近乎空白，但这**不是瓶颈**。真正缺的是适配器端口（见 P0-1）。对比同技术栈的
   AKStream（C# + ZLMediaKit），其 `MediaServerService.cs` 达 **294 KB** 且完全没有媒体
   抽象——VisiCore 最长的 `PonService.cs`（1717 行）远比它健康。以"行数"为由发动大重构
   缺乏证据支持，且会破坏目前唯一稳定的资产：已验证的业务行为。
2. **最高优先级不是架构，而是凭据泄露。** 生产 SSH/管理员/摄像机口令以**默认值形式硬编码
   并已进入 Git 永久历史**（commit `0d86a26`）。这是当前唯一需要立刻处理的问题。
3. **已有两项设计领先于同类开源项目**：SHA-256 校验的迁移机制优于 wvp-GB28181-pro 的
   "DBA 手工执行 SQL 文件"；手写 OpenAPI + 自研客户端生成器对单消费方私有化部署是合适选择。
   这两项**不应**为了"采用主流工具"而回退。

## 二、项目现状盘点

### 2.1 规模与构成（实测）

| 区域 | 规模 | 说明 |
| :--- | ---: | :--- |
| `src/` C# | 60,920 行 / 11 个项目 | 服务端 8 + 桌面端 3 |
| `tools/` C# | 37,400 行 | 验证工具与测试宿主 |
| `web-admin/`（不含生成物） | 29,944 行 | 27 个页面、12 个测试文件 |
| 生成客户端 | 2.4 MB C# + 740 KB TS | 单一 OpenAPI 契约产出 |
| `database/v2/` | 1,262 行 / 31 个迁移 | 嵌入式程序集资源，SHA-256 校验 |
| API 端点 | 18 个模块 / 178 个端点 | 95 处 `DemandAsync` 权限检查 |

### 2.2 分层现状

```
VideoPlatform.Domain        61 行   ← 仅 Rules.cs（权限常量/校验辅助）
VideoPlatform.Application   19 行   ← 仅 Ports.cs（3 个接口）
VideoPlatform.Infrastructure  所有业务逻辑（含 1073 行的 AdministrationService）
VideoPlatform.Api/Modules     直连 SQL（绕过 Domain/Application）
```

**这不是分层，而是"扁平单体 + 空目录"。** 但请注意：`ApiSupport`/`AccessService`/`Database`
构成的横切机制是有效且一致的，`Ports.cs` 里的 `IDeviceAdapter` 也是真实接口。
问题在于**只有 3 个接口**，而没有设备/媒体/资产等核心域的端口。

### 2.3 数据访问现状

`Database.cs` / `DbSession.cs` 提供 raw SQL → `JsonObject` 的访问方式，
参数通过**反射遍历匿名类型属性**绑定。全仓库约 **403 处** SQL 调用点。

关键澄清：**这不是 SQL 注入风险**。参数绑定是真实的 `NpgsqlParameter` + `AddWithValue`；
所有 `$"..."` 拼接的 SQL 只插入编译期常量片段（`ChannelPredicate`/`ChannelColumns` 等）；
所有动态标识符路径（`JobAuthorization.ForRow` 的别名白名单、`AssetScope`、
`OrganizationTable` 的穷尽 switch）都带抛异常的 default 分支。评审逐条追踪了污点路径，
**未发现用户输入进入 SQL 标识符的路径**。

真正的问题是**阻抗失配**：`JsonObject` 逐行手工取值（`row.Text()` / `row.Id()` /
`row.Time()`）导致每个查询都要写一遍映射，且字段名错误只能在运行时暴露。

| :--- | :--- | :--- |
| 全解决方案构建 | `dotnet build VisiCore.slnx -c Release` | ✅ **0 警告 0 错误**（17.9s） |
| Worker 测试 | `dotnet test tools/VideoPlatform.Worker.Tests` | ✅ 35 通过 / **33 跳过** |
| 适配器测试 | `dotnet run --project tools/VideoPlatform.Adapter.Tests` | ✅ 17/17 通过 |

| Web 单元测试 | `npm test --prefix web-admin` | ✅ 12 文件 / 91 项通过 |
| 集成回归 | `dotnet run --project tools/VideoPlatform.IntegrationTests` | ⚠️ **未处理异常退出** |

两点必须说明：

- **33 项跳过**全部来自同一个 `Skip = "未设置 WORKER_TEST_DATABASE_URL"` 的 PostgreSQL
  集成测试类。这与文档"缺少环境导致跳过的测试不能计作通过"的口径一致，**不应**被算作通过。
- **集成回归在无数据库/无 API 时直接抛未处理异常崩溃**（`HttpRequestException` 冒泡到
  `Main`），而不是优雅跳过。这是一个易用性缺陷：它会污染 CI 退出码，让"环境缺失"看起来
  像"测试失败"。建议改为检测到环境缺失时输出 `SKIP` 并返回 0。

### 2.5 值得肯定的设计

评审中确认这些是**真实实现且设计正确**，不是文档宣称：

- **`JobLocks` 咨询锁设计正确**（`JobRuntime.cs:53-88`）：使用**独立连接**持有会话级
  `pg_try_advisory_lock`，刻意置于事务之外；解锁失败时调用 `NpgsqlConnection.ClearPool`
  （`:84`），避免连接池归还后残留会话锁。这是该模式的正确写法。
- **`MediaService` 正确避免了"事务跨网络调用"反模式**（`MediaService.cs:34-96`）：事务内只做
  数据库操作，适配器调用在 **commit 之后**（`:73`），并在 catch 中补偿
  `StopInternalAsync`（`:92-96`）。
- **光网故障定界引擎是高质量业务逻辑**（`PonFaultClassifier.cs`，99 行）：把四级定界
  （Dying Gasp 供电 → 主干 → 分光器 → 单台）写成**纯函数**，时间窗（15s Gasp / 180s 并发 /
  30s 防抖）具名常量，并有 24 项回归矩阵（`docs/光网诊断规则与回归矩阵.md`）与真实边界测试
  （`GaspBoundary(15|16)`、`FullPortOutageNeedsConcurrentDownTimes(180|181)`）。
  `PortKey` 用 `neDn/机框/槽位/端口` 而非显示名分组，明确规避了跨 OLT 证据串联。
  **这是全仓库最值得保留和推广的写法。**
- **安全基础设施扎实**：PBKDF2-SHA512 210k 轮 + 常量时间比较 + SHA-256 令牌散列
  （`Security.cs:17-34`）；CSRF + 强制 HTTPS（`Program.cs:85-106`）；Cookie 为
  HttpOnly+Secure+SameSite=Strict；登录限流；`ForwardLimit=1` 且仅信任回环代理。
- **仓库卫生良好**：`git ls-files` 中**零**个 `.zip/.msi/.exe/.dll`；93 MB 的
  `JovisionClentSDK.zip` 已被正确忽略；4.8 MB `.git` 体积健康。

## 三、开源同类项目横向对比

### 3.1 对标项目

| 项目 | Stars | 技术栈 | 对本项目的参考价值 |
| :--- | ---: | :--- | :--- |
| [wvp-GB28181-pro](https://github.com/648540858/wvp-GB28181-pro) | 7,354 | Java + ZLMediaKit | ⭐ **最应参考**：多厂商抽象 + 媒体端口 |
| [AKStream](https://github.com/chatop2020/AKStream) | 1,538 | **C# + .NET + ZLMediaKit** | ⚠️ **反面教材**：同栈，但无抽象、文件 294 KB |
| [Frigate](https://github.com/blakeblackshear/frigate) | 36,564 | Python + go2rtc | 流采集与处理分离（[go2rtc 委托](https://docs.frigate.video/configuration/go2rtc/)） |
| [moonfire-nvr](https://github.com/scottlamb/moonfire-nvr) | 1,752 | Rust | 最强的内部 crate 边界纪律 |
| [ZLMediaKit](https://github.com/ZLMediaKit/ZLMediaKit) | 17,615 | C++ | 本项目已正确使用（HTTP Hook + REST） |

### 3.2 核心发现：wvp 的"命名策略端口"正是本项目所缺

wvp 用**一个端口接口 + N 个具名实现**解决多厂商问题，而非继续增加微服务：

```java
@Service("zlm") public class ZLMMediaNodeServerService implements IMediaNodeServerService { ... }
@Service("abl") public class ABLMediaNodeServerService implements IMediaNodeServerService { ... }
```

选择依据是**持久化的 `type` 判别列**（`MediaServer` 实体上的 `type: zlm/abl`），
而非上游 `if/else`。

**本项目现状对照**：`IDeviceAdapter`（`Ports.cs:13-16`）只有一个方法
`SendAsync(HttpMethod, string path, object? body)`——这是一个**泛型 JSON 透传**，
不是设备端口。`DeviceAdapter`（`DeviceService.cs`）的实现是**正则解析路径取 deviceId →
查 `device_plugins` 得到 `endpoint_url` → 转发**，并带一个 30 秒的静态缓存，
以及一个针对 `esight_pon` 的硬编码特例分支。

也就是说：**当前"驱动插件微内核"实质是"URL 路由表 + JSON 透传"**，
能力协商、健康语义、类型安全都不存在。海康与中维的差异没有在契约上表达出来。

### 3.3 明确的"不要做"

- ❌ **不要重写为 DDD/Clean Architecture**。空白 `Domain`/`Application` 不是瓶颈。
- ❌ **不要为 350 处 raw SQL 引入 EF Core**。正确解法在驱动层（见 P1-5）。
- ❌ **不要采用 wvp 的 Redis RPC 多节点架构**。本项目单机、11 台录像机、约 400 路，
  这是纯成本。
- ❌ **不要把 ZLMediaKit 做成插件**。Frigate 是委托 go2rtc 而非抽象它；
  wvp 抽象媒体服务器是因为它支持两种，本项目只有一种。**应抽象的是摄像机，而非媒体服务器。**
- ❌ **不要为摄像机适配器使用 `AssemblyLoadContext`**。适配器包装**原生 SDK**（HCNetSDK），
  原生句柄与 P/Invoke 使干净卸载几乎不可能；**进程外适配器是正确选择**，应保留。
- ❌ **不要把 OpenAPI/客户端生成或迁移机制换成"主流工具"**。这两项已领先对标项目。

## 五、优化路线图

### P0 — 立即（数天，确定性高）

1. **凭据处置**：轮换 SSH / 平台管理员 / 海康 / 中维四类口令 →
   移除 `os.environ.get(..., "真实口令")` 默认值改为 `os.environ["..."]` →
   `HANDOFF.md` 去敏（改为引用未跟踪的本地文件）→ `git filter-repo` 清历史并强制推送 →
